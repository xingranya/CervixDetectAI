## 结论摘要（必看）

当前项目存在多处**高风险安全与数据权限问题**，其中部分属于“明显可被利用”的 **IDOR（越权访问）/敏感数据暴露**，同时还存在**核心分析链路在某些流程下几乎必失败**的功能性缺陷。若计划对外部署或进入真实医疗数据场景，建议先按本报告的 **P0 清单**完成整改，再进行功能迭代。

### P0（建议立刻处理）的 10 个问题

- **P0-01**：`/uploads`、`/reports` 静态目录**无鉴权公开**，可直接下载患者影像与报告 PDF
- **P0-02**：患者数据权限隔离被显式取消：`/api/patients` 列表/详情/患者病例 **全员可见**
- **P0-03**：病例列表允许普通用户查看 `user_id = null` 的“匿名病例”，形成跨用户数据泄漏面
- **P0-04**：分析查询接口（`/api/analyze/:taskId`、`/api/analyze/study/:studyId`）缺少鉴权与归属校验，存在 **IDOR**
- **P0-05**：系统管理接口（`/api/system/*`）未鉴权：可获取数据库指标、触发清理、查询表大小
- **P0-06**：`/api/settings/*`、`/api/reports/*` 仍为 Mock 且**未鉴权**，包含写操作（POST/PUT）
- **P0-07**：工作台“历史任务”接口存在调试后门：普通用户在特定条件下可拿到**所有任务**（含患者信息）
- **P0-08**：JWT secret 存在不安全默认值（环境变量缺失时仍可运行），部署踩坑将导致 Token 可伪造
- **P0-09**：短信验证码明文写日志，属于敏感信息泄露（日志一旦外流风险极高）
- **P0-10**：`/api/studies` + `/api/analysis-tasks` 路线存在关键实现缺陷（`is_primary`、文件路径拼接），导致分析任务可能无法触发/必失败

## 分级标准

- **高风险（High）**：可导致敏感数据泄露、越权、支付权益异常、远程可利用安全问题、核心功能不可用
- **中风险（Medium）**：可能导致稳定性/性能问题、重要功能不一致、错误处理不当、维护成本显著升高
- **低风险（Low）**：代码风格/可读性、日志噪音、文档不一致、轻量重构与体验优化

## 高风险（High）

### H-01 [后端/安全] `/uploads`、`/reports` 目录通过 `express.static` 公开暴露（严重）

- **证据**
  - `server/index.js`：

```js
app.use('/reports', express.static(reportsDir));
app.use('/uploads', express.static(uploadDir));
```

- **影响**
  - 任意人（无需登录）可直接访问上传的影像与生成的 PDF 报告，属于**敏感医疗数据泄露**。
  - 一旦文件名/路径可被猜测或从接口返回中获得（例如 `StudyImage.file_path`），泄露面进一步扩大。

- **建议（最小改动）**
  - 立即移除公开 `express.static`，改为 **受控下载接口**：
    - `GET /api/files/study-images/:imageId`（需要 `authenticate`，并校验该 image 属于当前用户/医院）
    - `GET /api/files/reports/:reportId`（需要 `authenticate`，并校验归属）
  - 统一通过数据库表（`StudyImage`、`MedicalReport`）做归属校验，不允许客户端拼路径访问。

- **建议（最佳实践）**
  - 将上传文件存到对象存储（OSS/S3/COS），使用**短时签名 URL**或后端代理下载。
  - 对访问做审计：下载次数、下载时间、下载人。

- **验收点**
  - 未登录访问 `GET /uploads/*`、`GET /reports/*` 均返回 401/404（或不再存在路由）。
  - 登录用户只能下载自己拥有的文件，跨用户访问返回 403。

### H-02 [后端/合规] 患者数据权限隔离被显式取消（列表/详情/患者病例全员可见）

- **证据**
  - `server/routes/patients.js` 明确注释“权限调整：允许所有用户查看所有患者”，并注释掉创建者限制：

```js
// 权限调整：允许所有用户查看所有患者
// if (req.user.role !== 'admin') { where.created_by = req.user.id; }
```

- 患者详情同样注释掉归属校验：

```js
// if (req.user.role !== 'admin' && patient.created_by !== req.user.id) { return 403; }
```

- **影响**
  - 任一登录用户可检索/查看全部患者（含电话、身份证号、病史等字段），属于**高危隐私泄露**。
  - 即使项目标注“演示”，也建议把权限恢复，否则后续接入真实数据会“带毒上线”。

- **建议（最小改动）**
  - 恢复所有患者相关接口的归属校验（至少：非管理员仅能看 `created_by = req.user.id`）。
  - 若你希望“同医院可互看”，建议基于 `User.hospital_id` 做多租户隔离：
    - 患者表新增 `hospital_id` 或通过 `created_by -> User.hospital_id` 关联过滤。

- **建议（最佳实践）**
  - 引入**权限矩阵**：管理员/医生/普通用户，不同权限可见字段不同（字段级脱敏）。
  - 对 `id_card`、`medical_card_no` 等字段做**加密存储/脱敏返回**（见 M-05）。

- **验收点**
  - 非管理员访问他人患者：列表不出现、详情返回 403、患者病例返回 403。

### H-03 [后端/安全] 病例列表允许普通用户看到 `user_id = null` 的“匿名病例”（跨用户泄露面）

- **证据**
  - `server/routes/studies.js`：

```js
// 非管理员可以看到自己创建的病例 + 未分配用户的病例（匿名上传）
if (req.user.role !== 'admin') {
  where[Op.or] = [{ user_id: req.user.id }, { user_id: null }];
}
```

- `server/models/Study.js` 允许 `user_id` 为 `null`（支持匿名创建）。

- **影响**
  - 任一普通用户可看到所有“匿名上传”产生的病例（包含患者信息、影像路径、分析结果摘要），极易造成数据泄露。
  - 与 `H-04` 的分析接口 IDOR 叠加后，泄露面进一步扩大。

- **建议（最小改动）**
  - 去掉对 `user_id = null` 的开放查询；匿名病例应只对创建者可见（需要额外“匿名身份凭证”）。
  - 如果必须支持匿名：在 `Study` / `AnalysisTask` 增加 `public_token`（随机不可预测，短时有效），只有持 token 才可查询。

- **验收点**
  - 普通用户调用 `GET /api/studies` 只返回 `user_id = 自己` 的数据。

### H-04 [后端/安全] 分析查询接口缺少鉴权与归属校验（IDOR 可枚举）

- **证据**
  - `server/routes/analyze.js`：
    - `GET /api/analyze/:taskId` 无 `authenticate`/`optionalAuth`，直接查库并返回结果（包含患者 `name` / `patient_id`）。
    - `GET /api/analyze/study/:studyId` 同样无鉴权，允许用**数字自增主键**查询（`/^\d+$/`）。

- **影响**
  - 典型 **IDOR**：攻击者可以通过猜测/遍历 `studyId`（数字主键）直接拉取他人患者信息与分析结果。
  - 即使 `taskId` 为 UUID 也可能被日志/前端/截图泄露后复用查询。

- **建议（最小改动）**
  - 为上述两个接口增加 `authenticate`，并在查询时强制加入归属过滤：
    - `AnalysisTask.user_id = req.user.id` 或 `Study.user_id = req.user.id`
    - 管理员可放开
  - 如果必须“公开查询支付结果页”等场景，请使用**只读且脱敏**的公开接口，并基于一次性 token。

- **验收点**
  - 未登录请求全部返回 401。
  - 登录用户查询非本人 `studyId/taskId` 返回 403。

### H-05 [后端/安全] 系统管理接口未鉴权（数据库指标/清理/表大小）

- **证据**
  - `server/routes/system.js`：
    - `GET /db-metrics` 无鉴权
    - `POST /database/cleanup` 无鉴权，并存在 `TODO: 添加管理员权限验证`
    - `GET /database/size` 无鉴权

  - 允许任意触发“数据库清理”，属于**破坏性管理操作暴露**。

- **建议（最小改动）**
  - 对所有 `/api/system/*` 加 `authenticate`。
  - 对写操作（cleanup）加 `authorize('admin')`，并在生产环境默认禁用（可通过 env 控制开关）。

### H-08 [后端/安全] JWT Secret 存在不安全默认值，Refresh/Access 未分离

### H-10 [后端/功能] `/api/studies` + `/api/analysis-tasks` 分析链路存在关键缺陷（可能必失败）

该问题会直接影响“创建病例->上传影像->触发分析”的核心闭环。

- **证据 1：`is_primary` 默认 `false`，但触发分析时强依赖 `is_primary=true`**
  - `server/models/StudyImage.js`：`is_primary` 默认 `false`
  - `server/routes/studies.js` 上传影像创建 `StudyImage` 时未设置 `is_primary`
  - `server/routes/analysis-tasks.js` 触发分析时查找：

```js
StudyImage.findOne({ where: { study_id: study.id, is_primary: true } });
```

- **证据 2：文件路径以 `/uploads/...` 开头，`path.join(__dirname, '..', file_path)` 会被当作绝对路径**
  - `server/routes/studies.js` 存储 `file_path: "/uploads/studies/xxx"`
  - `server/routes/analysis-tasks.js`：

```js
const imagePath = path.join(__dirname, '..', studyImage.file_path);
```

在多数系统上这会变成 `"/uploads/..."`（根目录），而不是 `server/uploads/...`，导致读取文件失败。

- **影响**
  - 前端 `studyStore.createStudy()` 会调用 `analysisTaskAPI.createTask()`，但后端可能找不到主图或找不到文件，任务进入失败状态。
  - 此问题不但影响功能，还会制造大量失败任务与垃圾数据。

- **建议（最小改动）**
  - 上传影像时将第一张设为 `is_primary=true`（或在同一 study 内保证只有一张主图）。
  - 存储 `file_path` 建议去掉前导 `/`，统一存为相对路径（如 `uploads/studies/xxx`），读取时用 `path.resolve(serverRoot, file_path)`。

- **验收点**
  - 通过 `/api/studies` 创建病例并上传影像后，`/api/analysis-tasks` 创建任务能稳定进入 PROCESSING 并最终 SUCCESS。

### H-11 [配置/安全] 仓库中存在 `.env` 与 `server/.env` 文件，根目录 `.gitignore` 未忽略 `.env`

### H-12 [支付/安全] 支付权益发放缺少强幂等与并发保护（存在重复发放可能）

- **证据**
  - `server/services/paymentService.js`：
    - `handleNotify()` 与 `syncOrderStatus()` 都可能触发 `fulfillBenefits()`
    - `fulfillBenefits()` 仅用内存 `order.status` 早退，未对订单行加锁或做“仅一次更新”的原子判断

- **影响**
  - 回调重放/并发请求下，可能导致 `remaining_credits` 被重复累加（财务/权益风险）。

- **建议（最小改动）**
  - 在事务内重新查询订单并加行锁（`SELECT ... FOR UPDATE`），或使用原子更新：
    - `UPDATE orders SET status='paid' ... WHERE out_trade_no=? AND status!='paid'`
  - 仅当受影响行数为 1 时再发放权益。
  - 保存 `notify_data` 并记录已处理的 `trade_no`，防重放。

### H-13 [前端/安全] Access/Refresh Token 存储在 `localStorage`（XSS 场景可直接被盗用）

- **证据**
  - `src/stores/authStore.ts`：`localStorage.setItem('accessToken'...)`、`localStorage.setItem('refreshToken'...)`
  - `src/services/api.ts`、`src/services/apiClient.ts`：每次请求从 `localStorage` 取 token 注入 `Authorization`

- **影响**
  - 一旦出现任意 XSS（第三方组件、富文本、依赖漏洞、DOM 注入等），攻击脚本可直接读取 token 并冒用身份。
  - 在医疗/支付场景中，属于高风险会话劫持面。

- **建议（最小改动）**
  - 立刻补齐基础前端防护：减少/禁用不必要的 HTML 注入点、升级依赖、生产环境去除调试入口。
  - 增加 CSP（内容安全策略）与安全响应头（后端配合 `helmet`），降低 XSS 成功率。

- **建议（最佳实践）**
  - 将 refreshToken 迁移到 **HttpOnly + Secure + SameSite** Cookie（前端不可读），accessToken 尽量只放内存（Pinia state）。
  - 后端实现 refresh 旋转（rotation）+ 失效机制（黑名单/版本号/会话表），降低泄露后可用窗口。

### H-14 [后端/部署安全] 初始化脚本创建默认管理员账号/弱口令，并将口令明文打印日志

- **证据**
  - `server/scripts/init-database.js`：
    - 默认管理员邮箱：`admin@cervixdetectai.com`
    - 默认密码：`admin123456`

  - 初始化脚本禁止输出明文口令（仅输出“已创建管理员，请到控制台重置”）。

## 中风险（Medium）

### M-01 [前端/架构] Axios 客户端重复（`api.ts` 与 `apiClient.ts` 并存），拦截器/刷新逻辑不一致

- **证据**
  - `src/services/api.ts` 内部 `axios.create()` + refresh 逻辑 + `handleError()`
  - `src/services/apiClient.ts` 也创建了 `axios.create()` + refresh 逻辑（且重定向同为 `'/login'`）
  - 多处业务分别引用不同客户端（如 `patientService` 用 `apiClient.ts`，`studyStore` 用 `api.ts`）

- **影响**
  - Token 刷新、错误提示、超时配置可能出现不一致，导致“某些页面正常、某些页面异常”的隐性问题。
  - 维护成本高：修一次要改两份。

- **建议**
  - 选定唯一的 `apiClient`（建议以 `src/services/apiClient.ts` 为统一入口）。
  - `src/services/api.ts` 仅保留“按业务分组的 API 函数”，不要再创建新 axios 实例。

### M-02 [前端/稳定性] Token 刷新缺少并发锁（401 风暴时可能多次刷新/覆盖）

- **现象**
  - 多个请求同时 401 时会并发调用 `/auth/refresh`，可能导致刷新竞争、重复跳转登录、请求重放异常。

- **建议**
  - 引入“单飞”刷新机制：同一时刻只允许一个 refresh 在进行，其余请求等待同一个 Promise。

### M-03 [前端/路由] Hash 模式下使用 `window.location.href = '/login'` 可能跳转异常

- **证据**
  - `src/services/api.ts`、`src/services/apiClient.ts`：刷新失败后 `window.location.href = '/login'`
  - 项目路由模式为 `hash`（`quasar.config.ts`：`vueRouterMode: 'hash'`）

- **影响**
  - 生产静态部署时，`/login` 可能被服务器当成真实路径导致 404，正确应为 `/#/login`。

- **建议**
  - 使用 `window.location.href = '/#/login'` 或通过 router（需要避免循环依赖，可在 boot 层注入）。

---

### M-04 [前端/体验] `initializeAuth()` 可能晚于路由守卫执行，刷新后直达 `/app/*` 会被误重定向

- **证据**
  - `src/router/index.ts` 的 `beforeEach` 仅检查 `authStore.isAuthenticated`
  - `authStore.initializeAuth()` 在 `App.vue onMounted` 才调用

- **影响**
  - 刷新页面后直接访问 `/#/app/...`，守卫可能在 store 恢复前执行，从而跳转登录页（体验问题）。

- **建议**
  - 在路由守卫内做一次性初始化（例如首次进入时调用 `initializeAuth()`），或在 Quasar boot 阶段更早恢复。

---

### M-05 [后端/数据安全] 患者敏感字段声明“加密存储”但实际未加密，且接口直接返回

- **证据**
  - `server/models/Patient.js`：`id_card` 注释“加密存储”
  - `server/routes/patients.js` 返回 `patient` 全字段（默认包含 `id_card`、`phone` 等）

- **建议**
  - 至少做到：接口返回脱敏（如身份证仅保留后四位）。
  - 如涉及真实医疗数据：对 `id_card` 等字段做**应用层加密**（KMS/独立密钥），并限制查询与展示。

---

### M-06 [后端/安全] 缺少安全响应头（Helmet/CSP 等）与速率限制（Rate Limit）

- **现象**
  - 后端未引入 `helmet`，也未对登录/验证码/上传等接口做 rate limit。

- **影响**
  - 更易受基础 Web 攻击面影响（XSS 相关防护、MIME sniffing 等）。
  - 验证码接口与上传接口容易被刷，导致成本与可用性风险。

---

### M-07 [后端/可用性] `express.json/urlencoded` 允许 50MB 请求体，DoS 风险上升

- **证据**
  - `server/index.js`：`express.json({ limit: '50mb' })`

- **建议**
  - 将 JSON 请求体限制降到合理范围（如 1-5MB），文件上传使用 `multer` 限制即可。

---

### M-08 [后端/性能] 头像上传同步生成多尺寸图片，可能阻塞主线程

- **证据**
  - `server/routes/users.js`：一次上传生成 4 个尺寸，并在请求内完成 `sharp` 处理

- **建议**
  - 通过队列/worker 异步处理（BullMQ/Agenda/自建队列），请求先返回，后台再生成并更新 DB。

---

### M-09 [后端/一致性] 用户状态枚举与登录逻辑不一致

- **证据**
  - `server/models/User.js`：`status` 只有 `active/disabled`
  - `server/routes/auth.js`：登录校验使用 `inactive/suspended`（永远不会命中）

- **建议**
  - 统一状态枚举与判断逻辑，避免“禁用账号仍可登录”的误判。

---

### M-10 [短信/业务] 短信注册/登录对验证码 `type` 的使用存在不一致风险

- **证据**
  - `send-code` 可写入 `type=register`
  - `register` 校验时却固定查 `type='login'`

- **建议**
  - 明确策略：登录/注册共用一种 type 或各自独立，务必让“发送->校验”闭环一致。

---

### M-11 [后端/一致性] 任务/病例状态枚举混用（大小写与枚举值不一致），可能导致更新失败与清理失效

- **证据**
  - `server/models/AnalysisTask.js`：`status` 枚举为 `PENDING/PROCESSING/SUCCESS/FAILED`
  - `server/routes/analysis-tasks.js`：更新接口使用 `running/completed/failed/cancelled`（与枚举不一致）
  - `server/services/databaseCleanup.service.js`：清理任务使用 `status: ['completed', 'failed']`（与枚举不一致）
  - `server/models/Study.js`：病例 `status` 为小写枚举（`pending/processing/completed/failed`），与任务状态又是另一套

- **影响**
  - 任务状态更新接口可能触发 Sequelize ENUM 校验错误（接口“看似存在但不可用”）。
  - 清理服务可能长期清理不到真正的历史任务，导致数据库膨胀。

- **建议**
  - 统一约定：任务状态与病例状态分别定义清晰的枚举表（推荐统一大小写与命名规则）。
  - 后端对外输出与 DB 存储采用同一套枚举；若必须兼容旧值，在入口做映射与迁移。

---

### M-12 [前端/配置] `studyStore` 默认 API_BASE_URL 指向 3000，且字段映射与后端 schema 存在偏差

- **证据**
  - `src/stores/studyStore.ts`：
    - `const API_BASE_URL = import.meta.env.VITE_API_BASE_URL || 'http://localhost:3000/api';`
    - 但项目后端默认端口为 4000，且开发期主要依赖 Quasar proxy（`/api`）
  - 同文件中仍映射 `downloaded/downloaded_at` 字段，而后端 `Study` 模型已注明移除（存在 schema 不一致风险）。

- **影响**
  - 环境变量缺失时，图片 URL/接口可能走错端口，引发“本地正常/线上异常”的配置型问题。
  - 字段映射偏差会在后续你把报告下载状态真正落库时造成混乱。

- **建议**
  - 默认值优先使用 `'/api'`，并依赖环境变量在生产环境指向真实 API。
  - 为 `Study` 与 `AnalysisResult` 建立统一的 DTO 映射层（前端/后端一致），避免页面/Store 里散落字段拼装。

---

### M-13 [后端/运维] 请求异常时同步写入 `error.log`（无滚动/可能含敏感堆栈/阻塞事件循环）

- **证据**
  - `server/routes/analysis-tasks.js`：catch 内 `fs.appendFileSync(... error.stack ...)`

- **影响**
  - `appendFileSync` 会阻塞 Node 主线程；高并发下放大延迟。
  - 文件无限增长（无 rotation），可能导致磁盘写满。
  - 堆栈/错误信息可能包含路径、内部实现细节，甚至被动携带 PII（若错误链路包含请求数据）。

- **建议**
  - 使用结构化日志（pino/winston）+ 日志切割（rotate），并按级别输出。
  - 生产环境禁止写入包含敏感信息的堆栈到可被下载的目录。

---

### M-14 [业务/计费] 积分/订阅权益未在分析入口校验与扣减（可能导致无限制调用）

- **证据**
  - `server/models/User.js` 存在 `remaining_credits/subscription_expires_at` 等字段
  - `server/services/paymentService.js` 只负责“发放权益”，但在分析相关路由（`/api/analyze`、`/api/analysis-tasks`）中未发现扣减/校验逻辑

- **影响**
  - 若产品目标包含计费，当前实现会让分析能力“免费无限用”，带来成本与收入风险。

- **建议**
  - 在创建任务入口增加 `requireCredits` 中间件：
    - 校验订阅是否有效或积分是否足够
    - 在事务内扣减积分（失败可补偿/回滚）
  - 为匿名/公开入口（若保留）单独设置限流与配额策略。

---

### M-15 [后端/数据隔离] `/api/analyze` 以 `patientId` 全局唯一查找/复用患者，未按用户/医院隔离

- **证据**
  - `server/routes/analyze.js`：
    - `Patient.findOne({ where: { patient_id: patientId } })`（未加入 `created_by/hospital` 条件）

- **影响**
  - 不同用户/不同医院使用相同 `patientId` 时，会复用同一患者记录，形成数据串扰与越权基础面。

- **建议**
  - 明确 `patient_id` 的业务含义：
    - 若是“医院内编号”，应做复合唯一键：`(hospital_id, patient_id)`
    - 若是“用户内编号”，应限制在 `created_by` 维度唯一
  - 接口查询/创建时加入隔离条件，避免跨租户复用。

---

### M-16 [后端/统计] Dashboard 指标计算未按用户范围过滤，可能泄露全局统计且导致数据不准

- **证据**
  - `server/routes/dashboard.js`：
    - `highRiskCount = await AnalysisResult.count(...)` 未应用 `userCondition`
    - `diagnosisStats` 聚合时直接读取所有 `AnalysisResult`

- **影响**
  - 非管理员可能看到全局统计数据（间接信息泄露）。
  - 指标不准，影响产品判断与用户体验。

- **建议**
  - 通过关联 `Study.user_id` 或 `AnalysisTask.user_id` 做范围过滤（必要时 join）。
  - 若需要全局统计，仅管理员可见。

---

## 低风险（Low）

- **建议**
  - 统一日志策略：开发环境可打印，生产环境默认关闭或脱敏。
  - 用结构化日志（pino/winston）替代散落的 `console.*`，并避免打印患者 PII。

- **现象**
  - `docs/INTEGRATION.md` 明确提到部分接口为 Mock；而当前项目已经引入真实模型（`MedicalReport` 等），但路由仍是 Mock。

- **建议**
  - 明确“演示版/生产版”边界：通过 env 开关控制 Mock 路由，或尽快替换为真实实现并更新文档。

---

### L-03 [工程可维护性] `src/utils/storage.ts` 已提供类型安全封装，但多处仍直接使用 `localStorage`

- **建议**
  - 逐步替换为统一封装，减少散落 key 与 JSON 序列化错误。

---

### L-04 [版本一致性] Node 版本要求在 `package.json` 与 `README.md` 描述不一致

- **证据**
  - 根 `package.json`：`node: ^28 || ^26 || ^24 || ^22 || ^20`
  - `README.md`：Node >= 16

- **建议**
  - 以实际可运行版本为准统一文档，避免部署踩坑。
