## 一、执行摘要

### 1.1 核心结论

1. 路线方向正确，但阶段顺序需要重排：**先安全闭环，再去 Mock，再做功能扩展**。
2. 文档与代码状态存在偏差：部分任务已落地（如 `F1/F2/F8/F9/F10/F19/U11/T15`），需改为“验收优化”而非“从零开发”。
3. 当前最高风险仍是安全项：`S1/S2/S3/S6/S7/S8/S9/S10`。
4. 报告与设置模块仍有 Mock 残留，属于“功能看似可用、但不可交付”状态。

### 1.2 统一状态标记

| 状态 | 含义 |
| :-- | :-- |
| `✅ 已落地` | 已有实现，可直接进入验收与优化 |
| `🟡 部分落地` | 有骨架或局部实现，需补完关键链路 |
| `⚪ 待实现` | 尚无可用实现 |
| `🔴 高风险` | 安全或合规风险，必须优先处理 |
| `🚫 冻结` | 当前阶段不建议投入（低 ROI 或外部依赖过重） |

## 四、重排后的分阶段路线

> 说明：阶段按“价值/风险/依赖”重排，不再按原文顺序执行。

### P0：安全闭环（2-3 周）

**目标**：消除可被直接利用的安全风险，满足最小上线门槛。  
**范围**：`S1-S10`（全量），并完成关键验证脚本。

**完成标准**

- 未登录访问敏感接口返回 `401`。
- 越权访问他人数据返回 `403`。
- 无法直接通过静态路径访问患者影像/报告。
- Refresh Token 不可被 JS 读取。
- 支付回调重放不会重复发放权益。

### P1：去 Mock 与口径统一（1-2 周）

**目标**：让“看起来可用”的功能变成“真实可交付”。  
**范围**：`F14/F24/T8/T9/U14/U11/F1/F2/F8/F9/F10/F19/T15`。

**重点动作**

- 报告中心从 Mock 过渡到真实数据链路。
- 清理 dashboard 开发兜底逻辑，统一统计口径。
- API 服务层去重，消除 `api.ts` 与 `apiService.ts` 重叠。
- 优先清理高频页面 `any` 类型。
- F2/F8/F9 从“功能开发”切换到“体验验收与数据口径治理”。

### P2：架构收敛与质量基线（2-3 周）

**目标**：建立可持续迭代的工程底座。  
**范围**：`T1/T2/T10/T11/T13/U1/U2/U3/U4/U7/U17/F5`。

**重点动作**

- 落地 Migration，停止依赖 `sync({ alter: true })`。
- 建立最小单测集（认证、患者、分析任务、支付回调）。
- 统一主题变量与间距系统，减少样式漂移。

### P3：核心业务深化（3-5 周）

**目标**：提高医生侧效率与业务闭环完整度。  
**范围**：`F11/F13/F16/F18/F22/F26/U5/U6/U10/U12/U13/U15/U18/T16/T17`。

**重点动作**

- 患者时间线 + 历史对比进入“验收后优化”清单，不再作为从零开发项。
- 导入导出与操作审计，补齐运营和合规能力。
- 建立基本 CI/CD，接口文档与代码同步。

### P4：扩展能力与基础设施（4-8 周）

**目标**：在稳定基础上扩展协作、移动端与性能能力。  
**范围**：`F4/F6/F17/F20/F21/F23/F25/U8/U9/U16/U19/U20/U21/U22/T3/T4/T5/T6/T14/T18`。

### P5：长期演进（滚动规划）

**范围**：`T7` 等高投入长期项。  
**冻结项**：`F3/F7/F12/F15/T12`（仅保留调研，不进入近期排期）。

## 五、里程碑验收标准

### M1（P0 结束）

- 通过安全清单逐项复测，`S1-S10` 全闭合。
- 发布前安全回归脚本可重复执行。

### M2（P1 结束）

- 报告、设置、公告不再依赖 Mock 数据。
- 前端 API 调用入口统一，重复封装显著减少。
- 患者洞察（F2/F8/F9）完成稳定性验收，不再出现旧请求覆盖新患者状态。

### M3（P2 结束）

- Migration 可在新环境一键初始化。
- 核心路径单元测试通过并纳入日常流程。
- 主题与样式规范形成文档并落地首批页面。

### M4（P3 结束）

- 医生端关键业务流程（上传、分析、报告、随访、通知）全链路可演示。
- 审计日志可追踪关键操作。

### M5（P4 结束）

- Redis + 队列 + CI/CD + 监控形成稳定运行基线。
- 移动端核心交互可用。
